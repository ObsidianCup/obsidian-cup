## One-time setup

1. **Run the SQL:** Supabase → SQL Editor → New query → paste all of
   `SETUP-STAGE-1.sql` → Run. It is safe to run again.
2. **Login links:** Authentication → URL Configuration
   - Site URL: `https://obsidiancup.vercel.app`
   - Redirect URLs: add `https://obsidiancup.vercel.app/pages/account.html`
3. **Admin:** create an account on `/pages/account.html` with
   `obsidiancup.official@gmail.com` and confirm the email. That email is in
   `public.admins`, so `/pages/admin.html` then shows all players.
   To add another admin: SQL Editor → `insert into public.admins (email) values ('name@example.com');`

4. **Login with player code:** Edge Functions → Deploy a new function →
   Via Editor. Name it exactly `login-with-code`, replace the example code
   with all of `functions/login-with-code/index.ts`, Deploy. Then open the
   function's settings and turn **off** "Verify JWT" (visitors are not
   logged in yet) and save. No keys to paste: the function gets them from
   Supabase automatically. If you test from your own computer, the page must
   be on `https://obsidiancup.vercel.app` (or `http://localhost:8765`).

Supabase's built-in email sender only allows a few emails per hour. That is
fine for testing; before launch, set Gmail as the custom SMTP sender
(see `docs/SEASON-5-LAUNCH-PLAN.md`, section 9C).

## Reserving or changing a player code

In the SQL Editor (use lowercase emails; never commit personal emails to this repo):

```sql
-- reserve a code before the person saves their name
insert into public.reserved_player_codes (email, code)
values (lower('someone@example.com'), 'OC-UF023')
on conflict (email) do update set code = excluded.code;

-- change an existing code
update public.profiles set player_code = 'OC-UF023' where email = lower('someone@example.com');
```

Codes must look like `OC-` + 1–3 capital letters + 3–6 digits.

## Security rules in short

- Row Level Security is on for every table; nothing is visible unless a policy allows it.
- Players read and edit only their own profile, and only the columns granted
  in the migration. Player code, email, verification and guardian fields are
  not editable by players.
- Consent records are append-only and stamped on the server with the user,
  email, time and document fingerprint.
- Admin = confirmed email listed in `public.admins`; admin actions go through
  `admin_set_verified` and similar checked functions.
- Only the publishable key is in the website (`js/config.js`). The secret /
  service_role key must never be committed.

## Running the load test

Needs a real Postgres 15+ (Supabase uses 15/17). Example with a local server:

```
mkdir /tmp/loadtest && cd /tmp/loadtest && npm init -y && npm i pg
cp <repo>/supabase/tests/load_test.mjs . && PGHOST=<socket-dir> PGPORT=<port> PGUSER=postgres node load_test.mjs <repo> 1000
```

Last result (31 Oct 2026): 1,000 and 3,000 simultaneous players, no errors,
every player code unique. It found and led to the fix in
`004_code_concurrency.sql`.

## Limits to watch at launch (free plan)

- **Login emails:** Supabase caps how many auth emails go out per hour, even
  with custom SMTP (Authentication → Rate Limits; default is low). Raise it
  before opening registration, e.g. to 100/hour. Gmail itself allows about
  500 per day.
- **Sign-ups per IP:** a whole team signing up on one Wi-Fi network shares
  one IP address; keep the sign-up rate limit generous (Authentication → Rate Limits).
- **Login with player code:** these logins reach Supabase from the Edge
  Function, so they share Supabase's sign-in limit per address
  (Authentication → Rate Limits → sign-ins). Our own limit already stops
  password guessing (5 per code, 20 per address in 15 minutes), so raise the
  Supabase sign-in limit generously (e.g. 300 per 5 minutes) before launch.
- **Database:** 500 MB and 60 connections on the free plan; the load test
  ran 1,000 players through 60 connections in under 10 seconds.
